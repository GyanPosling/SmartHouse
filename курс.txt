2.1 Структура входных и выходных данных
В информационной системе «Умный дом» для каждого типа данных используется отдельный текстовый файл, что обеспечивает чёткое логическое разделение информации, упрощает её обработку и позволяет без труда интегрировать систему с внешними хранилищами.
Формат хранения полностью соответствует актуальной структуре классов: базовый класс Device определяет общие параметры (идентификатор, название, местоположение, уровень мощности, состояние включения), класс SmartDevice расширяет их данными о режиме работы (автоматический, ручной, выключен), а классы SmartLight, SmartHeater, SmartAirConditioner, SmartFan, SmartHumidifier, SmartDehumidifier содержат дополнительные поля и методы, уникальные для каждого типа умного устройства.
Файл devices.txt предназначен для хранения данных об умных устройствах в доме. Каждая строка содержит информацию об одном устройстве в следующем формате:
идентификатор|название_устройства|местоположение|режим_работы|уровень_мощности.
Режим работы указывается числом: 0 — автоматический режим, 1 — ручной режим, 2 — выключено. Уровень мощности представляет собой целое число, определяющее интенсивность работы устройства.

идентификатор|название_сенсора|значение|единица_измерения. Сенсоры используются для мониторинга температуры, влажности, уровня углекислого газа и других параметров, на основе которых умные устройства автоматически регулируют свою работу.

Каждая строка файла представляет собой отдельный объект и содержит данные, разделённые символом вертикальной черты (|), что обеспечивает корректность чтения и дальнейшую загрузку в контейнер. При запуске программы система загружает данные из всех файлов, создаёт соответствующие объекты и добавляет их в контейнеры, а при изменении данных перезаписывает файлы, обеспечивая актуальность и согласованность информации.

2.2 Разработка диаграммы классов
В результате анализа функциональности и структуры программы, а также алгоритмов и подходов, применённых в процессе разработки, была составлена диаграмма классов, отражающая архитектуру системы, иерархию объектов, их свойства, связи и используемые методы. Диаграмма демонстрирует взаимосвязь всех компонентов приложения и описывает принципы объектно-ориентированного проектирования, лежащие в основе системы.
Центральным элементом архитектуры является класс DeviceService, который организует управление данными, обрабатывает взаимодействие с файлами и обеспечивает доступ ко всем функциям программы, включая добавление новых устройств, редактирование их характеристик, удаление записей, фильтрацию и поиск по параметрам. Через него осуществляется координация между контейнерами объектов и файлами данных, а также обеспечивается автоматическое обновление устройств на основе показаний сенсоров.
Базовым элементом всей иерархии является класс Device, который объединяет общие поля для всех устройств в системе. Он содержит сведения об идентификаторе, названии устройства, местоположении, уровне мощности и состоянии включения, а также включает методы доступа и изменения этих данных. Этот класс служит фундаментом и обеспечивает единый интерфейс для наследников, позволяя унифицировать обработку объектов разных типов.
На основе класса Device формируется класс SmartDevice, который расширяет базовую структуру полем DeviceMode, определяющим режим работы устройства (автоматический, ручной или выключен). Класс SmartDevice служит промежуточным звеном в иерархии и содержит общую функциональность для всех умных устройств, включая виртуальный метод update() для автоматического обновления состояния на основе параметров окружающей среды.
От класса SmartDevice наследуются специализированные классы, каждый из которых представляет отдельный тип умного устройства. Класс SmartLight описывает осветительные приборы с возможностью регулировки яркости. Класс SmartHeater реализует функциональность обогревателей с автоматической регулировкой температуры. Класс SmartAirConditioner представляет кондиционеры с умным управлением климатом. Класс SmartFan описывает вентиляторы с автоматической регулировкой скорости. Класс SmartHumidifier реализует увлажнители воздуха, а класс SmartDehumidifier — осушители воздуха. Каждый из этих классов переопределяет метод update() для реализации специфической логики автоматического управления на основе показаний сенсоров.
Для хранения и обработки коллекций устройств используется специализированный контейнер DeviceContainer, реализованный на основе std::vector. Он обеспечивает добавление, удаление и перебор объектов и предоставляет удобный доступ к элементам через встроенный итератор. Контейнер поддерживает поиск по различным полям (идентификатор, название, местоположение, режим, уровень мощности) и сортировку устройств по заданным критериям.
Для представления сенсоров используется класс Sensor, который содержит идентификатор сенсора, его название, текущее значение и единицу измерения. Класс User описывает пользователей системы и включает идентификатор, имя пользователя и пароль. Класс EnvironmentSimulator хранит информацию о параметрах окружающей среды (температура, влажность, уровень CO2) и обеспечивает симуляцию изменений этих параметров для тестирования автоматического управления устройствами.
Обмен данными с файловой системой реализован через механизм чтения и записи объектов в отдельные текстовые файлы. Для каждого типа данных существует свой файл: devices.txt, users.txt, sensors.txt. Каждая строка файла представляет собой один объект, включающий свойства конкретного класса. При запуске системы данные считываются из файлов и загружаются в контейнеры через классы-репозитории (DeviceRepository, UserRepository, SensorRepository), а после выполнения пользователем операций добавления или редактирования обновлённые сведения сохраняются обратно в файлы, что обеспечивает согласованность данных и их доступность при повторном запуске программы.
Для реализации механизма отмены и повторения действий используется класс CommandHistory, фиксирующий операции пользователя, такие как добавление, изменение или удаление объектов. Действия помещаются в стек команд, что позволяет восстановить предыдущее состояние программы и обеспечивает удобство работы, повышая устойчивость и надёжность приложения. Система поддерживает отмену и повторение нескольких последовательных операций.
Таким образом, диаграмма классов комплексно отражает структуру системы «Умный дом», демонстрируя многоуровневое наследование, связи между объектами, поддержку хранения данных, функциональные возможности контейнера и принципы работы системы управления данными. Диаграмма иллюстрирует взаимодействие всех элементов программы и служит наглядным подтверждением правильности выбранной архитектуры. С финальной диаграммой классов можно ознакомиться в Приложении А.

2.3 Описание классов

Программная реализация информационной системы «Умный дом» построена на объектно-ориентированном подходе, что обеспечивает структурированность, гибкость и расширяемость архитектуры. Основой логической структуры является многоуровневая иерархия классов, отражающая деление умных устройств на категории и обеспечивающая возможность их однородной обработки. В проекте реализованы базовые и специализированные классы, каждый из которых отвечает за представление конкретной сущности предметной области, хранение её характеристик и взаимодействие с системой.
Центральным элементом иерархии является базовый класс Device, содержащий общие поля для всех устройств в системе: int id, std::string deviceName, std::string location, int powerLevel и bool isOn. Эти данные определяют идентификатор устройства, его название, местоположение в доме, уровень мощности и состояние включения. Класс предоставляет методы для установки и получения значений полей, а также виртуальные методы turnOn(), turnOff() и getDeviceInfo() для управления устройством и вывода информации. Он служит базовой основой для всех производных типов и обеспечивает единый интерфейс взаимодействия.
От класса Device наследуется класс SmartDevice, который представляет умное устройство и дополняет базовые характеристики полем DeviceMode mode, отражающим режим работы устройства (автоматический, ручной или выключен). Класс SmartDevice предоставляет методы для работы с режимом работы и виртуальный метод update(double temperature, double humidity, double co2, int hour) для автоматического обновления состояния устройства на основе параметров окружающей среды и времени суток.
От класса SmartDevice наследуются специализированные классы. Класс SmartLight представляет осветительные приборы и реализует логику автоматической регулировки яркости в зависимости от времени суток и уровня освещённости. Класс SmartHeater описывает обогреватели и автоматически управляет температурой в помещении. Класс SmartAirConditioner представляет кондиционеры с функциональностью охлаждения и поддержания заданной температуры. Класс SmartFan описывает вентиляторы с автоматической регулировкой скорости на основе температуры и влажности. Класс SmartHumidifier реализует увлажнители воздуха, автоматически поддерживающие оптимальный уровень влажности. Класс SmartDehumidifier описывает осушители воздуха, удаляющие избыточную влагу из помещения. Каждый из этих классов переопределяет виртуальный метод update() для реализации специфической функциональности автоматического управления.
Для хранения объектов в программе используется специализированный контейнер DeviceContainer, представляющий собой обёртку над std::vector<shared_ptr<SmartDevice>>. Контейнер обеспечивает операции добавления, удаления, последовательного доступа через встроенный итератор, а также предоставляет возможность расширения функционала сортировкой и поиском по различным параметрам (идентификатор, название, местоположение, режим, уровень мощности). Контейнер используется для хранения записей об умных устройствах.
Класс Sensor описывает сенсоры системы и содержит поля int id, std::string sensorName, double value и std::string unit. Класс предоставляет методы для работы с показаниями сенсоров и используется для мониторинга параметров окружающей среды. Класс User хранит информацию о пользователях системы и включает поля int id, std::string username и std::string password. Класс EnvironmentSimulator обеспечивает симуляцию параметров окружающей среды и содержит методы для получения текущих значений температуры, влажности и уровня CO2, а также для обновления этих параметров.
Работа с внешними данными осуществляется через классы-репозитории (DeviceRepository, UserRepository, SensorRepository), которые организуют загрузку и сохранение данных из текстовых файлов. Информация об устройствах сохраняется в файле devices.txt, о пользователях — в users.txt, о сенсорах — в sensors.txt. Каждый файл содержит записи, сформированные на основе полей соответствующих классов. При запуске программы данные загружаются из файлов в контейнеры через методы loadAllDevices(), loadAllUsers(), loadAllSensors(), а при изменениях — записываются обратно через методы saveDevice(), saveUser(), saveSensor(), обеспечивая постоянство информации.
Класс DeviceService координирует работу всех компонентов системы, обеспечивает взаимодействие между контейнерами устройств и репозиториями, а также реализует автоматическое обновление устройств на основе показаний сенсоров через метод updateAllDevices(). Класс CommandHistory реализует механизм отмены и повторения действий пользователя. Он хранит сведения о произведённых операциях, включая добавление, редактирование и удаление объектов, и позволяет восстановить предыдущее состояние данных через методы undo() и redo(). Данный механизм повышает удобство работы и предотвращает потерю информации.
Все классы вместе формируют целостную архитектуру, включающую многоуровневое наследование, механизм хранения и обработки данных, поддержку взаимодействия с пользователем, автоматическое управление устройствами и инструменты управления изменениями. Такая структура обеспечивает надёжность, логичность и удобство дальнейшего расширения программы.



3  ФУНКЦИОНАЛЬНОЕ ПРОЕКТИРОВАНИЕ
3.1 Разработка схем алгоритмов (два наиболее важных метода)
В информационной системе «Умный дом» ключевую роль играют методы, обеспечивающие обработку данных и их синхронизацию между внутренними структурами хранения и внешними текстовыми файлами. Для корректной работы приложения особенно важными являются алгоритмы чтения климатических данных из файлов и нормализации климатических условий на основе доступных устройств. Оба метода определяют основу функционирования программы, поскольку именно они обеспечивают работу с климатическими данными, их загрузку из файлов и автоматическую нормализацию параметров окружающей среды. Ниже представлены описания их логики и последовательности выполнения.
Чтение климатических данных из файла является одним из фундаментальных процессов системы, так как именно через этот механизм система получает информацию о текущих параметрах окружающей среды (температура, влажность, уровень CO2) для последующей обработки и нормализации. Метод readFromFile() класса ClimateFileManager открывает текстовый файл с климатическими данными, построчно считывает значения параметров и создаёт объект ClimateData с полученными значениями.
Алгоритм начинается с валидации имени файла и проверки его существования через метод validateFile(). Затем производится открытие файла для чтения. Если файл не может быть открыт, выбрасывается исключение FileException. После успешного открытия файла система последовательно читает три строки: первая строка содержит значение температуры, вторая — значение влажности, третья — уровень CO2. Каждое значение преобразуется из строки в число с плавающей точкой с помощью функции stod() с обработкой возможных ошибок преобразования. При отсутствии какой-либо строки или некорректном формате данных выбрасывается соответствующее исключение с описанием проблемы. После успешного чтения всех параметров файл закрывается, и функция возвращает объект ClimateData с загруженными значениями.
Такой алгоритм обеспечивает надёжную загрузку климатических данных из файлов и гарантирует корректность обработки информации. Он также позволяет системе работать с различными источниками климатических данных и обеспечивает обработку исключительных ситуаций при работе с файлами.
Метод нормализации климатических условий является одним из самых важных элементов системы, поскольку он обеспечивает автоматическую корректировку параметров окружающей среды на основе доступных в системе умных устройств. Алгоритм состоит из нескольких последовательных этапов, каждый из которых направлен на определение возможности нормализации того или иного климатического показателя и установку целевых значений.
Процесс начинается с создания копии текущих климатических данных и определения целевых значений (температура 25.0°C, влажность 30.0%, уровень CO2 400.0 ppm). Затем система анализирует список доступных устройств, определяя наличие устройств каждого типа (обогреватели, кондиционеры, увлажнители, осушители, вентиляторы) с помощью dynamic_cast. После этого для каждого климатического параметра проверяется, находится ли он в нормальном диапазоне. Если параметр выходит за пределы нормы, система проверяет наличие соответствующего устройства для его корректировки. Если устройство присутствует, параметр нормализуется до целевого значения; если устройство отсутствует, параметр остаётся без изменений.
Такой подход обеспечивает реалистичность нормализации: система нормализует только те показатели, для которых есть соответствующие устройства, что делает процесс более практичным и отражает реальные возможности системы управления умным домом.

3.2 Разработка алгоритмов (описание алгоритмов по шагам, для двух методов)
Алгоритм 1. Чтение климатических данных из файла:

Шаг 1. Начало.
Запуск функции readFromFile() класса ClimateFileManager для чтения климатических данных из указанного файла.

Шаг 2. Валидировать имя файла.
Вызывается метод validateFile() для проверки корректности имени файла. Проверяется, что имя файла не пустое, и что файл существует и доступен для чтения. При обнаружении ошибок выбрасывается исключение FileException.

Шаг 3. Открыть файл для чтения.
Создаётся объект ifstream и выполняется попытка открытия файла с указанным именем. Если файл не может быть открыт, выбрасывается исключение FileException с кодом 200 и описанием ошибки.

Шаг 4. Инициализировать объект ClimateData.
Создаётся пустой объект ClimateData для хранения загруженных климатических параметров.

Шаг 5. Прочитать температуру из первой строки.
Выполняется чтение первой строки файла с помощью getline(). Если строка отсутствует, выбрасывается исключение FileException с кодом 201. Значение температуры преобразуется из строки в число с плавающей точкой с помощью stod(). При ошибке преобразования выбрасывается исключение FileException с кодом 202. Полученное значение устанавливается в объект ClimateData через метод setTemperature().

Шаг 6. Прочитать влажность из второй строки.
Выполняется чтение второй строки файла. Если строка отсутствует, выбрасывается исключение FileException с кодом 203. Значение влажности преобразуется из строки в число с помощью stod(). При ошибке преобразования выбрасывается исключение FileException с кодом 204. Полученное значение устанавливается в объект ClimateData через метод setHumidity().

Шаг 7. Прочитать уровень CO2 из третьей строки.
Выполняется чтение третьей строки файла. Если строка отсутствует, выбрасывается исключение FileException с кодом 205. Значение CO2 преобразуется из строки в число с помощью stod(). При ошибке преобразования выбрасывается исключение FileException с кодом 206. Полученное значение устанавливается в объект ClimateData через метод setCO2().

Шаг 8. Закрыть файл.
Файл закрывается, освобождая ресурсы системы.

Шаг 9. Вернуть объект ClimateData.
Функция возвращает объект ClimateData, содержащий все загруженные климатические параметры (температура, влажность, уровень CO2).

Шаг 10. Конец функции.
Климатические данные успешно загружены из файла и готовы к использованию.


Алгоритм 2. Нормализация климатических условий

Шаг 1. Начало.
Запуск функции normalize() класса ClimateNormalizer для нормализации климатических показателей на основе доступных устройств.

Шаг 2. Инициализировать нормализованные данные.
Создаётся копия текущих климатических данных (ClimateData normalized = currentData) для последующей модификации.

Шаг 3. Определить целевые значения.
Устанавливаются фиксированные целевые значения: температура 25.0°C, влажность 30.0%, уровень CO2 400.0 ppm.

Шаг 4. Инициализировать флаги наличия устройств.
Устанавливаются булевы переменные hasHeater, hasAirConditioner, hasHumidifier, hasDehumidifier, hasFan в значение false.

Шаг 5. Проанализировать список устройств.
Выполняется перебор всех устройств из переданного вектора. Для каждого устройства с помощью dynamic_cast определяется его тип (SmartHeater, SmartAirConditioner, SmartHumidifier, SmartDehumidifier, SmartFan) и устанавливается соответствующий флаг в true.

Шаг 6. Проверить и нормализовать температуру.
Если температура не находится в нормальном диапазоне (MIN_TEMP - MAX_TEMP), проверяется её значение. Если температура ниже минимума и есть обогреватель (hasHeater == true), устанавливается целевая температура. Если температура выше максимума и есть кондиционер (hasAirConditioner == true), устанавливается целевая температура. Если соответствующего устройства нет, температура остаётся без изменений.

Шаг 7. Проверить и нормализовать влажность.
Если влажность не находится в нормальном диапазоне (MIN_HUMIDITY - MAX_HUMIDITY), проверяется её значение. Если влажность ниже минимума и есть увлажнитель (hasHumidifier == true), устанавливается целевая влажность. Если влажность выше максимума и есть осушитель (hasDehumidifier == true), устанавливается целевая влажность. Если соответствующего устройства нет, влажность остаётся без изменений.

Шаг 8. Проверить и нормализовать уровень CO2.
Если уровень CO2 не находится в нормальном диапазоне (MIN_CO2 - MAX_CO2), проверяется его значение. Если CO2 выше максимума и есть вентилятор (hasFan == true), устанавливается целевой уровень CO2. Если вентилятора нет, уровень CO2 остаётся без изменений. Случай, когда CO2 ниже минимума, обычно не требует нормализации.

Шаг 9. Вернуть нормализованные данные.
Функция возвращает объект ClimateData с нормализованными показателями, которые могут быть достигнуты с помощью имеющихся в системе устройств.

Шаг 10. Конец функции.
Нормализация завершена, возвращены климатические данные с учётом возможностей системы.
